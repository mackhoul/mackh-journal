# Защита удалённых сделок — как включить

Что даёт: если запрос на сохранение сделки пришёл на сервер позже, чем её
удаление (например, после долгого ожидания), удалённая сделка больше не
воскресает. База сама помнит удаление. «Отменить» снимает только то удаление,
которое отменяет пользователь, — более новое удаление старая отмена не снимет.

Сначала прочитайте целиком. Делайте шаги строго по порядку.

## 0. Перед стартом

- Миграцию лучше один раз прогнать на **тестовом** проекте Supabase с такой же
  таблицей `trades` (без ваших настоящих сделок) и только потом — на рабочем.
- Изменения ветки `fix/trade-save-delete` должны пройти ревью.

## 1. Резервная копия

**а) Строки таблицы.** Supabase → **Table Editor** → `trades` → **Export → CSV**.
Важно: CSV — это только копия строк. В нём нет структуры таблицы, ключей,
индексов, функций, прав и настроек проекта.

**б) Структура таблицы.** Supabase → **Table Editor** → `trades` → вкладка
**Definition** → скопируйте показанный SQL и сохраните рядом с CSV.

**в) Полная копия** (по желанию, надёжнее всего): **Database → Backups**
(на платном тарифе) или `supabase db dump` из Supabase CLI.

Проверка восстановления — отдельный шаг: убедитесь, что CSV открывается и в нём
столько строк, сколько в таблице.

## 2. Миграция базы — пока работает СТАРЫЙ сервер

1. Supabase → **SQL Editor** → **New query**.
2. Вставьте весь файл `db/migrations/2026-10-21-trade-deletion-guard.sql`.
3. **Run**. Ожидаемо: `Success. No rows returned`. Повторный запуск безопасен.

Почему сначала база: нынешний (старый) сервер про новые колонки не знает и
продолжает работать как сегодня — ничего не ломается и ничего нового не
происходит. А новый сервер, запущенный уже после миграции, сразу работает
только в защищённом режиме: незащищённых записей с его стороны не будет.

## 3. Проверка базы

В том же SQL Editor:

```sql
select public.mj_guard_selftest();
```

Ожидаемо: `{"ok": true, "save": "saved", "wiped": true, "late_save": "deleted", "old_undo": "deleted", "undo": "saved"}`.
Самопроверка работает на выдуманной строке и всё за собой откатывает —
таблица не меняется. Если `ok` не `true`, не переходите к шагу 4.

## 4. Новый сервер

`server.js` попадает на Render, когда ветка слита в `main` (ваше отдельное
решение после ревью). Render перезапустится сам.

## 5. Проверка сервера

Откройте `https://mackh-journal.onrender.com/health/db`. Нужно оба:

- `"deletion_guard": true` — колонка на месте;
- `"deletion_guard_selftest": { "ok": true, ... }` — сервер с его ключом
  действительно может вызвать функции базы (права и RPC работают).

Если `deletion_guard_selftest.ok` не `true` — не пользуйтесь удалением и
пришлите этот ответ на разбор.

Если сервер не может достучаться до базы (временная ошибка, нет прав), он
теперь **отказывает в сохранении** (ошибка 500, приложение повторит позже),
а не пишет по-старому без защиты.

## Что меняется для данных

- Удалённая сделка не стирается из таблицы целиком: остаётся строка-отметка
  с ID, владельцем, датой `deleted_at` и номером `deleted_gen`. Содержимое
  (`data`) и ссылка на скриншот стираются. Сам файл скриншота в хранилище,
  как и раньше, не удаляется.
- Приложение такие строки не показывает.
- Старые версии приложения продолжают работать: попытка сохранить удалённую
  сделку получает ответ «ок, пропущено» и не создаёт её снова.

## Если порядок перепутан

Если новый сервер выкатили раньше миграции, он работает по-старому и каждые
10 секунд проверяет, появилась ли миграция; не позже чем через ~10 секунд после
её запуска включает защиту. В эти секунды удаление работает как сегодня
(без защиты). Поэтому лучше соблюдать порядок 2 → 3 → 4.

## Откат

В конце SQL-файла есть закомментированный блок «Rollback»: он удаляет функции,
строки-отметки и обе колонки. Это возврат к старому поведению, а не
восстановление удалённых сделок — их содержимое было стёрто при удалении
(вернуть можно только из резервной копии шага 1). После отката перезапустите
сервер на Render (**Manual Deploy → Restart**), чтобы он сразу перешёл в старый
режим.
