Обе проверки проходят только на тестовом проекте `mackh-journal-test` (ref `ibjjethbdgawqnttqmvc`) и на локальном сервере `http://127.0.0.1:3010`. Production Supabase, Render, `main` и настоящие сделки не используются. Каждый шаг сначала записывает ожидаемый результат, а потом фактический.

## A. Интерфейс приложения против staging-сервера

**Подготовка (делает Claude).**
- Во временную папку (не в Git) копируется `index.html`. В копии меняется одна строка: `const SERVER = 'https://mackh-journal.onrender.com'` на `'http://127.0.0.1:3010'`.
- Копия раздаётся статическим сервером на `http://127.0.0.1:8080`, его CORS сервер уже разрешает.
- Перед входом в журнале сети проверяется, что нет ни одного запроса к `onrender.com` и к рабочей Supabase. Если такой запрос есть — стоп.
- localStorage тестового адреса перед началом очищается.

**Вход (делает Андрей).**
- Claude не вводит пароли.
- Андрей сам открывает `.env.staging` в Блокноте и входит в браузерной панели как `test-a@example.com`.
- Пароль в чат не присылается.

**Сценарии.** Claude нажимает кнопки, Андрей смотрит. После каждого сценария сверяем три вещи: экран, ответ сервера в журнале сети и строку в базе (её через service key читает только Claude).

| # | Сценарий | Ожидание (критерий PASS) |

| A1 | Создать сделку | Сделка видна, статус синхронизации «сохранено». В базе 1 строка, `deleted_at` null |

**После.**
- Строки, созданные этими сценариями, удаляются по точным парам (id, user_id) с повторным чтением, как в скрипте.
- Временная копия `index.html` удаляется.
- В отчёте: таблица ожидание/факт, статусы и коды без токенов, отдельный список того, что не проверено.

## B. Репетиция отката SQL и повторного включения

Цель — проверить на тестовой базе, что откат из конца миграции работает, что происходит с сервером до и после перезапуска и что защиту можно включить обратно.

| # | Шаг | Кто | Ожидание (критерий PASS) |
|---|---|---|---|
| B1 | Снимок до отката: все строки `trades` тестового проекта, через service key, в память и во временную папку вне Git | Claude | Число активных строк и меток удаления записано |
| B2 | Подготовка: сделка X активна; сделка Y удалена через сервер (метка, `deleted_gen = 1`) | Claude через локальный сервер | В базе одна активная строка и одна метка |
| B3 | Выполнить блок Rollback из конца `2026-10-21-trade-deletion-guard.sql` в SQL Editor тестового проекта | Андрей (вставляет блок, Claude даёт текст) | Success. Функций `mj_*` нет, колонок `deleted_at` и `deleted_gen` нет |
| B4 | До перезапуска сервера: `GET /trades`, сохранение X | Claude | Ожидаемо 500: сервер всё ещё считает защиту включённой (`server.js`, «ON stays ON»). Это подтверждает, что в рабочем откате перезапуск обязателен |
| B5 | Перезапустить локальный сервер | Claude | `/health/db` → `deletion_guard: false` |
| B6 | Старый режим: сохранить, изменить, удалить новую сделку | Claude | Всё работает. X на месте и не изменилась. Y исчезла совсем (метка удалена откатом). Содержимое Y не восстанавливается — так и описано в DEPLOY |
| B7 | Сравнить с B1 | Claude | Все активные строки совпадают по всем колонкам, кроме двух удалённых колонок. Исчезли только метки удаления |
| B8 | Повторно выполнить всю миграцию | Андрей | Success |
| B9 | `select public.mj_guard_selftest();` | Андрей | `ok: true` |
| B10 | Без перезапуска сервера подождать 10 с, затем `/health/db` | Claude | `deletion_guard: true` и `selftest.ok: true` (OFF проверяется заново каждые 10 с) |
| B11 | Полный `02-staging-checks.cjs` с CSV | Claude | Код 0 |
| B12 | Убрать строки B2 и B6 по точным парам, с повторным чтением | Claude | Ничего лишнего не осталось |

**Условия остановки.** Любой результат, отличный от ожидания, или ошибка SQL. Тогда дальше не идём, фиксируем состояние и решаем вместе.

**Что это даст для рабочего развёртывания.**
- Проверенный порядок отката: SQL откат → немедленный перезапуск сервера → проверка `/health/db`.
- Подтверждение, что откат не трогает активные сделки и не возвращает содержимое удалённых.

## Не входит в этот план

- Render, Telegram-бот, загрузка и удаление картинок в R2. Их можно проверить только после разрешённого развёртывания или на отдельных тестовых ресурсах.
- Рабочее включение (свежая копия данных, окно изменения, миграция → selftest → новый сервер → health). Готовится отдельно и выполняется только после решения Андрея.
